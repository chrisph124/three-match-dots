# Anchor / weight obstacle

## Trigger

User chose "start new feature work" → new obstacle. First pick "guardian cage" was found already
shipped (the multi-layer cage IS "guardian" — see Evidence 1), so the user redirected to the next
genuinely-unbuilt catalog obstacle: **anchor / weight**.

## Evidence (scouted from code, not intent)

1. **"Guardian cage" is already built.** `src/core/obstacles/caged-dot.ts` is a fully general
   multi-layer cage (`layers ≥ 1`, sheds one layer per same-colour clear, pops on the last). Every
   `guardian` mention in the repo literally reads "multi-layer guardian cage"
   (`plans/260824-1106-voyage-infinite-mode/plan.md:58`, `phase-04-...:59`,
   `src/core/voyage/archetypes.ts:45`) — it was the pre-ship codename for the multi-layer cage, which
   shipped as "layered cages". Building a "guardian" obstacle now would be redundant.
2. **Anchor is a real catalog entry, not yet in the schema.** `docs/three-dots-game-design.md:137`
   (obstacle catalog): **Anchor / weight** — "Occupies a cell, falls with gravity but isn't linkable;
   cleared by an adjacent chain per rule (tunable)." Only `cagedDot` is in the validated zod schema +
   engine today; the rest (anchor, locked tile, colour lock) are catalog-only.
3. **Anchor ≠ the cage's resolve seam.** `resolveChain(state, chain, protectedCells)`
   (`src/core/resolve/resolve-chain.ts`) exposes a generic `protectedCells` seam: a protected cell
   _links + counts on the full chain_ but resists removal (the cage seam). **Anchors do not fit it** —
   an anchor is never linkable, and is removed by an _adjacent_ clear, which means emptying a cell that
   was NOT in the chain (it must then fall + refill). That is a deeper integration than cages needed.
4. **Linkability is decided by colour match in the worklet hot path.** `canAppend`
   (`src/core/hot/can-append.ts`) rejects a cell when `board[cell] !== board[chain[0]]` — `'worklet'`,
   allocation-free, strict rules. cagedDot never touched it (caged dots stay linkable). To make anchors
   unlinkable **without** changing the worklet signature, suppress them one level up in the input
   hit-test (`src/input/`), so `canAppend` never sees an anchor cell.
5. **The overlay pattern is proven and one-directional.** cagedDot is a `Map<CellIndex, number>`
   overlay with `buildCaged` / `chipLayers` / `remapMoves`, bridged by `resolve-caged-chain.ts`, folded
   in `journey-state.ts` + `voyage-state.ts`, modelled by `solver.ts`, generated by `generate-level.ts`.
   Anchor mirrors this exact spine (a `Set<CellIndex>` — single-hit, no layers).
6. **The design doc's ORIGINAL caged text described this mechanic.** The layered-cage brainstorm
   (`260824-2239-...:30`) noted `three-dots-game-design.md:132` once described the caged dot as the
   classic Two-Dots anchor ("can't be linked while caged, freed by adjacent same-colour clears"). Cages
   deliberately took the _linkable/layered_ branch instead; the **anchor obstacle realises that
   not-taken branch as a distinct obstacle** — non-redundant.

## Delivery contract

- **Outcome:** Level authors (Journey) and the generator (Voyage) can place **anchors** — paper
  "weights" that occupy a cell, are **not linkable**, **fall with gravity**, and are **removed by any
  8-way-adjacent same-colour clear** (single-hit); the freed cell then empties → falls → refills. A new
  `clearAnchors` objective completes when the board holds no anchors. Generated levels stay provably
  winnable.
- **Constraints:**
  - **Approach ① (overlay).** Anchor = a `Set<CellIndex>` overlay; the underlying board cell keeps an
    unused real colour so gravity/refill/board invariants are untouched. Suppress linking in the
    **input hit-test** (`src/input/`), NOT in `canAppend` — the worklet `hot/**` path stays byte-identical.
  - **Protect the tested colour core** (`src/core/resolve/**`, `src/core/hot/**`): no new value in the
    `Board` domain (that is the cagedDot discipline; Approach ② was rejected for breaking it). Any
    resolve change is a generic, mechanic-agnostic seam in the same spirit as `protectedCells` — the
    core never learns "anchor".
  - Core stays RN-free (Vitest-pure); render math stays geometry-pure (`src/render/geometry.ts`).
  - **One rule, two callers:** the removal rule (`removeAdjacent`) is a pure function shared by the
    runtime fold AND the solver — no drift (the level-83 divergence lesson).
  - Solver must model anchors (unlinkable cells + adjacency-removals) so every generated level stays
    winnable; budgets re-calibrated (anchors change the move economy).
  - Tuning constants (anchors per difficulty band) live in `src/core/voyage/voyage-config.ts` only.
  - Anchor art stays paper-craft per the LOCKED `docs/creative-bible.md` (one implied top-left light,
    soft paper shadow); drawn in a **sibling overlay layer**, board canvas untouched (the cage-overlay
    pattern).
  - Files ~<200 lines; kebab-case; no `any`; no AI attribution in commits/PRs/comments; no em-dashes in
    on-screen copy.
- **Non-goals (this work):**
  - No multi-hit / weight-N anchors (single-hit only; weight-N is the cage's identity).
  - No sink-to-bottom "exit the board" gravity model.
  - No specific-colour-vulnerability anchors (8-way any colour only).
  - No new biome or palette; **Endless mode untouched**.
  - No general multi-obstacle framework; no locked-tile / colour-lock (separate future obstacles);
    Android.
- **Acceptance (on-device — worklet/native, not Vitest-testable):**
  - Anchors render as visible paper weights with the remaining count of anchors surfaced (HUD, like
    cages).
  - An anchor cannot be linked into a chain; dragging over it does not break a valid chain around it.
  - An anchor falls with gravity and is preserved (in place) across a deadlock reshuffle.
  - Any 8-way-adjacent same-colour clear (plain chain, loop-sweep, or line-sweep) removes the anchor;
    its cell then refills with a normal dot.
  - `clearAnchors` completes only when every anchor is gone; a level with anchors is winnable within its
    (re-calibrated) budget.
  - Endless is visually + behaviourally unchanged.
- **Automatable gate (pre-handoff to owner):** new/updated Vitest suites for `obstacles/anchor.ts`
  (removal rule, 8-way adjacency, gravity/shuffle remap), the objective fold (`clearAnchors`), schema
  accept/reject (`anchor` obstacle + `clearAnchors` objective), and solver winnability sweep;
  `npm run lint` / `typecheck` / `test` / `coverage:diff` green; `src/core/**` RN-free.

## Chosen direction — Approach ① overlay (recommended shape)

- **Overlay type:** `Set<CellIndex>` in state (anchored cells). New `src/core/obstacles/anchor.ts`:
  `buildAnchors(cells)`, `removeAdjacent(anchors, clearedIndices, cols)` → `{ removed, survivors }`
  (pure, 8-way, shared by runtime + solver), `remapAnchors(anchors, moves)` (gravity/shuffle remap,
  mirrors `caged-dot.ts` `remapMoves`).
- **Unlinkable:** the input hit-test returns "no cell" over an anchored cell, so a chain can never
  include one and `canAppend` / `hot/**` need no change. A drag that passes over an anchor simply does
  not register on that cell.
- **Removal + refill in one pass:** after `resolveChain` produces `cleared` (pre-gravity indices),
  compute anchors 8-way-adjacent to any cleared cell; those anchor cells are added to the set emptied
  **before** gravity/refill, so removed anchors fall + refill in the SAME resolution (one animation
  pass). Removed-anchor cells score 0 and do NOT count toward colour objectives — a third category
  beside `cleared` and `protectedHits`. Exact mechanism (a generic `expandCleared` seam in
  `resolveChain` vs a dedicated `resolve-anchor-chain.ts` wrapper) is R1 below — settle in planning.
- **Objective:** `journey/objectives.ts` gains a `clearAnchors` branch — done when the anchor set is
  empty (mirrors `freeCaged`).
- **State folds:** `voyage-state.ts` + `journey-state.ts` thread the anchor set through commit →
  removal → gravity/shuffle remap, exactly as they thread `caged`.
- **Solver + generator:** `solver.ts` / `enumerate-moves.ts` model anchors as unlinkable cells and
  count adjacency-removals toward `clearAnchors`; `generate-level.ts` + `archetypes.ts` +
  `difficulty-budget.ts` place anchors per band (counts in `voyage-config.ts`).
- **Render:** new sibling anchor-overlay layer over the board (both `journey.tsx` + `voyage-game.tsx`),
  paper weight per anchored cell; HUD shows remaining anchor count. Board canvas untouched.
- **Docs:** promote anchor from catalog-only to a live schema entry in `docs/level-script-schema.md`;
  note it in `docs/three-dots-game-design.md`; update the `src/` architecture map if a new module lands.

## Risks

- **R1 (highest) — emptying a non-chain cell mid-resolve without touching `hot/`.** cagedDot never
  changed the board on freeing (the dot was already in the chain); an anchor removal must empty a cell
  that was NOT in the chain, then fall + refill it, ideally in ONE gravity pass. Options for the
  planner: (a) a generic `expandCleared(cleared) → extra cells` seam on `resolveChain` (one pass, one
  animation, same spirit as `protectedCells`; touches the tested `resolveChain`); (b) a
  `resolve-anchor-chain.ts` wrapper that recomputes collect + does gravity/refill itself (keeps
  `resolveChain` untouched but duplicates orchestration); (c) two-pass wrapper (rejected — double fall
  animation + remap reconciliation). Recommend (a). **Settle before coding.**
- **R2 — solver winnability + budget recalibration.** Anchors gate cells and add removal work; the
  winnability sweep + move/time budgets must be re-run or generated levels become unwinnable (the
  level-83 false-halt lesson — the solver is load-bearing).
- **R3 — sweep interaction.** A colour-sweep (2×2 loop / ≥5 line) clears many cells at once, so it could
  remove many anchors via adjacency in one move. Confirm on device that mass anchor removal by a sweep
  feels intended (recommend: yes — consistent with "any adjacent clear removes it").
- **R4 — deadlock / reshuffle.** Anchors reduce linkable cells, so `hasLegalMove` must count only real
  linkable dots (ignore anchors) or the board may over- or under-reshuffle; shuffle must keep anchors
  in place, not scatter them.
- **R5 — input feel.** Dragging a chain across/around an anchor must feel natural (the anchor is a dead
  zone, the chain routes around it) — verify on device.
- **R6 — tone.** Anchor art must stay within the LOCKED creative bible (paper, restrained, top-left
  light); joins the pending on-device render sign-off queue.
